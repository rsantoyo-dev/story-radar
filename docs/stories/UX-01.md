# UX-01 — Build shared visual primitives and resolve one Topic theme

**Status:** In progress · **Priority:** P0  
**Feature:** [Consistent interface and editorial experience](../features/ui-ux-consistency.md)  
**Dependencies:** None

As an editor, I want familiar controls and the same Topic appearance on every screen, so moving between setup and production feels predictable.

## Current evidence

The four panel modules define separate control styles. The dashboard passes the creative profile to topicThemeStyle, while the Story route passes only the theme key. Help has another shell without Topic theme resolution.

**Surfaces:** [uxdsl.config.js](../../uxdsl.config.js) · [uxdsl.config.cjs](../../uxdsl.config.cjs) · [uxdsl.theme.config.cjs](../../uxdsl.theme.config.cjs) · [topic-themes.ts](../../src/design/topic-themes.ts) · [radar-dashboard.module.uxdsl](../../src/app/radar-dashboard.module.uxdsl) · [creative-draft-workspace.module.uxdsl](../../src/app/creative-draft-workspace.module.uxdsl) · [editorial-profile-panel.module.uxdsl](../../src/app/editorial-profile-panel.module.uxdsl) · [topic-configuration-panel.module.uxdsl](../../src/app/topic-configuration-panel.module.uxdsl).

## Acceptance criteria

1. Define shared Button, IconButton, Surface, SectionHeader, FormField, StatusBadge, InlineNotice, EmptyState, LoadingState, Tabs, and action-row contracts. Use accessible native elements and keep domain decisions out of these primitives.
2. Document variants and sizes from the feature's visual contract. Equal-rank controls in a row share height, typography, radius, and spacing. Primary, secondary, quiet, and destructive actions are visibly distinct in all supported Topic themes.
3. Create a safe component showcase containing normal, hover, focus, disabled, busy, error, and long-label cases. Reuse existing UXDSL tokens and build orchestration; add an entry only if needed.
4. Resolve the effective Topic palette consistently for dashboard, Story route, Help, dialogs, and any portal. Preserve brand palette settings and historical artwork. Show a stable fallback while required theme data loads.
5. Migrate representative consumers from each of the dashboard, creative studio, and configuration families. Remove the superseded rules for migrated controls; document remaining migration targets in the audit.
6. Verify computed token values, readable text, icon alignment, focus contrast, and control geometry using at least two contrasting Topic themes. Do not infer visual correctness from a successful CSS build.

## Validation

Compare the same control states across the three migrated families at 390 and 1440 px. Open one Topic in dashboard, studio, and Help and confirm the same effective palette. Verify an unavailable creative profile uses the documented fallback.

## Scope and delivery

This defines shared presentation; it does not change Topic brand ownership or creative image styling.

Apply the feature's [shared visual contract and definition of done](../features/ui-ux-consistency.md), including UXDSL, English UI copy, responsive/keyboard checks, and preservation of approvals and history. Record implementation and visual evidence before changing status. The [component audit](../ui-ux-component-audit.md) lists every affected consumer.

## Implementation evidence — September 27, 2026

- Shared primitives and a UXDSL build entry now cover the contracts above. The local `/ui-showcase` displays both Press green and Signal blue with disabled, busy, error, focus, and long-label fixtures. It returns 404 in production.
- Dashboard production actions, the studio's brief action, and the Topic form actions use the shared Button. Dashboard queue-specific rules were removed; the configuration panel excludes shared Buttons from its legacy descendant rule.
- Dashboard, Story, and Help resolve the same stored brand-derived palette on the server. A read-only lookup avoids creating a creative profile. In a local browser, the selected Topic produced identical `primary` (`#071426`) and `dark` (`#00193E`) values on all three routes.
- [390 px showcase](../evidence/UX-01/showcase-390.png) and [1440 px showcase](../evidence/UX-01/showcase-1440.png) include two Topic themes and the relevant states. Browser measurements: no horizontal overflow at either width; primary button 44 px at 390 and 40 px at 1440; compact button 44 px at 390 and 36 px at 1440; 14 px labels and a 3 px visible focus outline. Computed primary label contrast is 6.41:1, secondary label contrast is 11.31:1, and the focus color contrasts 12.64:1 with the white surface. The initial browser check found unreadable semantic tones and mobile overflow; both were corrected before these captures.
- In the authenticated built app, Topic form actions measured 44/40 px, dashboard production actions 44/36 px, and the studio brief action 44/40 px at 390/1440 respectively, all with 14 px labels. Equal-rank actions within each row matched. All three screens had no page-level horizontal overflow after constraining the studio's profile and research selects. A focused test confirms the Topic-key fallback when no creative profile is available.
